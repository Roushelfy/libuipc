# SOCU Native Contact Conventions

These rules are written so they can be checked by tests, source scans, reports,
or benchmark scripts.

## Hot Path Rules

1. Direct production replay must not call `reporter->assemble(hessian_info)`.
   Reporter triplet assembly is allowed only in `triplet_compat` and
   diagnostic/compatibility modes such as `direct_compare` and counted `hybrid`
   fallback.
2. Native contact executor hot paths must not include or call
   `structured_contact_assembly_sink.h`, legacy target-table builders,
   `old_to_chain`, or `classify_dof_pair`.
3. Numeric replay must consume a valid symbolic plan. Empty contact topology is
   a native no-op, not a reason to fall back to legacy contact TUs.
4. Cache-hit steady state must not rebuild side or program plans.
5. `direct` mode must reject unsupported direct programs or count them as an
   error; `hybrid` mode is the only mode allowed to fall back, and it must update
   `native_contact_direct_unsupported_program_count` and
   `native_contact_direct_fallback_program_count`.

## ABD Projection Rules

Builder-generated ABD side lanes must match the legacy structured sink
projection:

- for `q < 3`, `component = q` and `weight = 1`;
- for `q >= 3`, `component = (q - 3) / 3` and
  `weight = x_bar((q - 3) % 3)`.

Manual writer fixtures are not enough. A contract test must inspect lanes
generated by the symbolic builder, not only hand-written plans.

The builder must receive the ABD Jacobi/projection source (`abd_vertex_to_J`) and
materialize side-lane weights from `ABDJacobi::x_bar()`. Missing projection data
must not silently degrade into `component = q, weight = 1` for ABD lanes.

`SocuNativeMatrixBuilder` snapshots and host-copy helpers are allowed in tests,
debug snapshots, and symbolic setup checks. They must not become the direct
production replay path for per-frame contact numeric data.

## Scalar Diagonal Compatibility Rules

`native_contact_scalar_diag_compat=1` is a behavior flag, not only a cache key or
report field. When the flag is enabled and a diagonal fallback cannot be emitted
as a full native block, the builder must emit `DiagScalarFem` or
`DiagScalarAbd` tasks and report scalar diagonal task counts.

`native_contact_scalar_diag_compat=0` keeps the block-diagonal policy unless the
program is dropped or rejected by the selected offband policy.

## Cache Key Producer Rules

`fixed_mapping_epoch` and `vertex_projection_epoch` must be real producer
signals. If descriptor epoch intentionally covers fixed mapping and ABD
projection changes, that ownership must be documented and tested. Otherwise the
producer must populate these epochs so mapping or `x_bar` changes invalidate both
side and program plans.

## Source Ordering Rules

Source ids are dense and stable within one build of the contact source table.
The ordering must be identical for:

- symbolic builder inputs;
- topology stamp hashing;
- direct evaluator source entries;
- triplet compatibility evaluator entries;
- direct compare reference entries.

The shared host helper `collect_socu_contact_source_catalog` is the source of
truth for current plan input, topology stamp, direct source, direct-compare
reference, and `triplet_compat` reference ordering. Source-scan tests must
reject new per-consumer source id counters.

## Header And Build Rules

The current direct evaluator and executor are known header-heavy risks. This is
accepted only as an M6.6/M6.7 transition state.

Before M8 cutover:

- broad public headers should contain POD/view types and launcher declarations;
- heavy contact math, kernels, and family-specific evaluator implementations
  should move into `.cu` translation units or narrow implementation headers;
- native-only build graph checks must show that legacy structured contact hot
  paths are not production dependencies of direct native replay.

## Report Rules

Reports must expose enough fields to distinguish bridge, direct, and diagnostic
paths:

- `native_contact_replay_path`;
- `native_contact_evaluator_path`;
- `native_contact_plan_cache_hit`;
- `native_contact_plan_cold_start`;
- `native_contact_plan_rebuilt_this_solve`;
- `native_contact_plan_build_ms`;
- `native_contact_direct_eval_ms`;
- `native_contact_hessian_triplet_ms`;
- `native_contact_executor_scatter_ms`;
- `native_contact_hot_reduce_ms`;
- `contact_assembly_time_ms`;
- `native_contact_direct_compare_mismatch_count`.

## Benchmark Claim Rules

A speedup claim is invalid unless it records:

- exact command and environment variables;
- binary path and CMake cache;
- git commit and branch;
- GPU, driver, and CUDA toolkit;
- scene, variant, frame count, and seed when applicable;
- warmup policy;
- at least three repeated runs and median values;
- subsystem timing fields, not only end-to-end wall time.
